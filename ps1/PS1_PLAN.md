## 2. Feasibility of translating Payback

### 2.1 Measured (analyze_rom.py, census2.py, t2m_census.py; outputs `*.out`)
Recursive-descent from the ROM entry (ARM `b` at 0x08000000 -> crt0 -> `bx` to Thumb main 0x08022dc9), literal-pool aware, const-propagating `bx`:
- Thumb code: 156,988 instructions = 329,450 bytes, span 0x08000000..0x0807c9e0 (4% of the 8 MiB ROM). Essentially all of the ROM-resident code is Thumb (only the 10 crt0 ARM instructions are ROM-resident).
- IWRAM code: crt0 copies ROM 0x087d9bf4 (3.1 KiB) and 0x087da83c..0x087e077c (24.4 KiB) to 0x03000000.. : about 27.5 KiB = 6,882 words, 6,861 decode as ARM (21 are data). That is Payback's ARM hot code (mul/asr/ldr/add heavy). merge.ld's hot..hot11 describe the same area.
- Instruction mix (Thumb): ldr 16.9%, adds 12.2%, movs 11.6%, str 8.9%, cmp 6.5%, mov 5.5%, lsls 5.2%, bl 4.9%, b 3.9%, ldrsh 2.9%, subs 2.3%, strh 2.0%, beq/bne 3.2%, muls 1.2%.
- BIOS SWIs: 1 in all reachable code (SWI 5, VBlankIntrWait); none in the IWRAM image. Payback has its own divide/copy code. The BIOS layer is trivial.
- Hardware register literals (0x04000xxx) in ROM code: DISPSTAT 16, VCOUNT 7, BG2 affine regs 0x20-0x2c ~48, BLD 6, SOUNDCNT_X 1, FIFO_A 2, DMA2/3 regs ~10, timers 0x100/104/10c, serial 0x120-0x12a (10), KEYINPUT 5, IE/IF/IME ~24. Code that builds 0x04000000 as `movs 4; lsls 24` is not in this count, so true IO sites are higher (to be counted by the translator in stage 1).
- Indirect control flow: 423 `bx/blx rN` (341 not resolved statically = function-pointer calls and `pop {r1}; bx r1` returns), 27 `mov pc,rN`, 83 `pop {pc}`. Pointers stored as data all hit already-found code (pass 2 seeded 0 new targets), so the call graph from the entry is closed except IRQ entry, tables read at run time and the 341 pointer calls; those targets come from ROM pointer tables (seeded by scanning for 0x08xxxxxx words). Self-modifying code: none seen statically; memmap.txt (from run-time write watches) says Payback never writes its IWRAM code. Jump tables: `add pc` only 0 sites in Thumb (switches compile to compare chains/`mov pc`, 27 sites).
- Translated size (t2m.py, model A = every unknown-base access does an inline region fold, 9 words): 156,988 Thumb -> 375,314 MIPS words = 1,466 KiB, x2.39. Per Thumb instruction: 0 words 6.5% (nops), 1 word 53.4%, 2 words 22.6%, 3 2.8%, 4 1.2%, 5 0.3%, 6+ 13.1% (memory with dynamic base, calls with nop, bx). Memory accesses: 39,899 non-literal; base constant-known region 10%, sp-relative 39%, dynamic 51%. 13,793 literal loads become `li` (1-2 words).
- Model B (host-pointer model, see 3.1: translated constants are already host addresses, so a dynamic access is 1 word, plus ~3 for the ROM/IO window check where the base could be ROM): about 0.9-1.1 MiB, x1.7. Delay-slot filling would cut ~10% more. Not built yet; this is an estimate from the A numbers (20,416 dynamic accesses x 5 words saved).
- Unsupported in the prototype (728 sites, 0.5%): ldm 191, stm 133, hi-register/PC forms 27, adr 8, coprocessor/vfp junk (data decoded as code) ~24, svc 1, `bx rN` 341. ldm/stm/adc/sbc/ror and register shifts >= 32 need helpers or 3-6 word expansions.

### 2.2 Proof (proof.py, `proof.out`)
Two real Payback functions from the user's ROM, strlen (0x08077d34) and a strcmp-like (0x08077d78), translated to MIPS-I by t2m.py (push/pop of lr, byte loads through the region fold, cmp+bcc fused into beq/bne, loop, return through a popped lr) and run on unicorn-MIPS32LE against the original Thumb on unicorn-ARM, 300 random cases each (lengths 0..40, mismatches planted): returns and the whole 256 KiB RAM image identical, PASS. 14 Thumb insns -> 33/34 words; executed MIPS/ARM = 2.54x and 2.94x (model A, dominated by the 9-word dynamic access). Limits of the proof: unicorn MIPS32 is not an R3000 (no load-delay slot, no cache): the translator must add a pass that inserts a nop when the word after a load reads its destination (not written yet; `lbu` followed by `beq` in these functions is exactly that case). It was not run in PCSXR. Only 2 functions, no calls, no flags beyond cmp+bcc.

### 2.3 Decision: full static recompile, no interpreter for the main path; hybrid only as a cold-path fallback
- Interpreter speed: an ARM/Thumb interpreter on the R3000 costs roughly 25-40 MIPS instructions per guest instruction (fetch, decode via table, operand fetch, flag handling, write back). The GBA ran about 10-13 M Thumb instr/s at full load; 10 M x 30 = 300 M MIPS instr/s against about 25 M/s available (33.8 MHz, ~0.75 IPC with a 4 KiB I-cache). Ten times too slow, so an interpreter cannot carry Payback.
- Translated: 2.4x (A) / 1.7x (B) means 10 M guest instr/s need 17-24 M MIPS instr/s. That is the GBA at 100% load. Payback's own logic was only part of that load (our engine did the drawing on the GBA CPU; on the PS1 the GTE/GPU takes it). Assuming Payback logic is 30-50% of a GBA frame (UNMEASURED; stage 1 profiles it) it needs about 5-12 M MIPS instr/s = 20-50% of the R3000 at 24 fps. Feasible but tight; the Payback tick can also run at 15 Hz while drawing at 24+.
- RAM: 1.0-1.5 MiB of translated code does not fit 2 MiB beside GBA RAM (EWRAM 256 K + IWRAM 32 K shadow = 288 K), VRAM/pal/OAM shadows (~110 K), engine (~150 K), stack/OT/GPU lists (~150 K), CD/SPU buffers (~100 K). So code is overlay-paged from CD in groups (by call-graph cluster: menus/phone/missions/init are cold) into a ~700 KiB overlay arena; the hot set (traffic, people, AI, collision, physics glue) stays resident. Stage 1 profiles (unicorn GBA harness) to choose the split. CD seeks (~150-300 ms) are hidden by loading overlays at mode switches (menu <-> game, map load) and a pre-load of the cluster for the current mission.
- Fallback interpreter (about 2 KiB of MIPS for the Thumb subset plus ARM data-processing subset) only for the unresolved indirect targets that the table scan misses and for self-test; never on the hot path.
- Legal shape: the translator runs on the user's PC/phone-side build step from their ROM; no Payback code or data enters the repo. Only the translator, runtime and our engine live in the repo.

## 3. Architecture

### 3.1 Memory map and addresses
- PS1 RAM 2 MiB at 0x80000000. Layout: 0x80010000 resident code (runtime + engine + hot translated code), 0x80100000 EWRAM image 256 KiB (guest 0x02000000), 0x80140000 IWRAM 32 KiB (guest 0x03000000), 0x80148000 shadow pal 1 KiB, OAM 1 KiB, IO shadow 1 KiB, VRAM shadow 96 KiB (only modes Payback uses; the engine draws on the GPU instead), then overlay arena, ordering tables, CD buffers, stack at the top (0x801fff00).
- Host-pointer model (B): the translator rewrites every constant of region 0x02/0x03 (literals and mov/lsl-built bases) into the host address, so pointers held by the program are host pointers and loads/stores are direct. IO/pal/OAM/VRAM constants map to shadow windows in the same RAM (writes to IO/pal/OAM are caught only at the sites that are known IO sites, found by the translator; they call helpers: `io_write16(reg,val)` etc.). ROM constants (0x08...) split by role: code pointers stay guest addresses (looked up through a sorted entry table, `jal rt_lookup`), data tables that Payback logic reads are copied into RAM or an overlay-like data cache; bulk assets (textures, models, music, maps) are read through helpers from the CD. Risk R2: code that compares pointers against region constants or does unaligned loads (ARM rotates; MIPS needs lwl/lwr) - the translator logs both.
- Return addresses: `bl` sets lr to a host address (`jal` writes $ra; we use $28 as lr); `bx lr`/`pop {pc}` are `jr`. Function-pointer calls and tables hold guest addresses and go through the lookup.
- Registers: r0-r7 -> $16-$23, r8-r12 -> $11-$15, sp -> $30, lr -> $28; temps $1,$2,$3,$8-$10,$24,$25; $k0/$k1 untouched (interrupts); flags lazy (cmp+bcc fused; 0.1% of branches in the sample needed a helper; the real census of flags live across blocks is stage-1 work).

### 3.2 Graphics
- Our 3D engine (stuntfox/src: render.c, citydraw.c, model.c, car.c ...) keeps its data model; the back end changes from the GBA mode-5/affine bitmap rasteriser to: GTE transforms (RTPT/RTPS, NCLIP, AVSZ3/4), polygons built as GPU packets (POLY_F3/G3/FT3/FT4) inserted into a 1024-entry ordering table (two OTs, double buffered), sent by DMA channel 2 linked-list. Textures: Payback's and ours into VRAM texture pages (4-bit/8-bit CLUT, cell textures 64x64 per cell colour), CLUT rows in the right half. 320x240 or 368x240, 15-bit, 24+ fps.
- engine/gpu_ps1.c interface: `gpu_begin_frame()`, `gpu_tri(x[3],y[3],z,col|uv,tpage,clut)`, `gpu_quad(...)`, `gpu_sprite(...)`, `gpu_end_frame()`. `engine/gte.h` macros (the ones in hello/main.c). The engine's existing r_* functions are re-pointed, the fixed-point formats (4096 = 1.0) are already GTE-like.
- Payback's 2D (menus, HUD, text, minimap): Payback draws these by writing tile/bitmap/OAM/palette memory. The shadow VRAM/OAM/pal windows are converted each frame: tilemaps and OBJ sprites become GPU textured quads/sprites (a tile = 8x8 sprite from a tile atlas in VRAM), BG bitmap layers upload to a VRAM page. Highest-risk piece after the translator (many modes); stage 3 starts with the menus' mode only.

### 3.3 Sound and music
- SPU: Payback's samples/instruments are not used as is: Payback's mixer writes PCM into DMA buffers (FIFO_A). The translated mixer output is replaced by `sound_ps1.c` feeding SPU RAM ring buffers via DMA (22/32 kHz mono as SPU ADPCM is not possible for live PCM; SPU PCM streaming trick = 16-bit not supported, so use CD-XA/CD-DA for music and SPU ADPCM voices for SFX encoded at build time from the ROM's samples).
- Music: CD-DA tracks. Track list: Payback songs 0 (title remix, nu metal), credits (djent), the three Payback remixes (songs 1,2,4), the 11 tracker-module remix radio edits (full-length versions, `/mnt/project-files/stunt-fox/music/mods/` and `music/remixes-ps1/`) and Payback's originals rendered from the ROM. Budget: 74 min audio; the 11 edits are 828 s, plus ~3 remixes and title/credits ~12 min: fits. Radio: pad SELECT+R cycles, the runtime issues CD `Play track N` (CDROM cmd 0x03) with CDDA volume via the SPU CD input; loop with the CD report-mode end-of-track interrupt. Seek ~1 s when switching: acceptable for a radio. Audio files are produced at build time on the user's side; never committed.

### 3.4 Input, saves, loading
- Input: DualShock digital/analog via SIO0 polling each vblank (own driver in runtime: command 0x42 poll, ids 0x41/0x73); map D-pad/Cross/Circle/Square/Triangle/L1/R1/L2/R2/Select/Start to GBA KEYINPUT bits (A,B,L,R,Select,Start), the extra buttons give new inputs (camera, bail-out). Analog sticks for steering/camera in the engine.
- Saves: Payback saves to flash/EEPROM through IO + byte routines; the translator detects those routines and replaces them with `save_ps1.c` writing 1 block memory card slot (SIO0 memory card protocol, own driver; format with the standard 128-byte directory frame header and "SC" icon) from an in-RAM image. Android emulators emulate cards, so users get this for free.
- Loading: boot ISO has SYSTEM.CNF, PSX.EXE (runtime + resident code), overlay files (OVL*.BIN), assets (WORLD.BIN, TEX.BIN), SFX; read with the CD controller in polled mode (CDROM regs 0x1F801800), double speed, sector = 2048. Own ISO9660 reader (root directory only) or fixed LBA table written by the build tool (preferred: no filesystem code).

### 3.5 What changes on the PS1 (user wishes)
- Ragdolls: tools/ragdoll_ps1_ref.c is the solver as a self-contained C file (PC reference, `python3 tests/s2/ragdoll_ps1.py`). On the PS1 it is compiled with the same clang flags (fixed-point already) and run per-bone with the GTE helping on matrix rotations; target several full-body ragdolls (not 1-2 bodies/half a frame as on the GBA). Stage 5: port it as `engine/ragdoll_ps1.c`, measure cycles per body per tick with the PCSXR cycle counter (rcnt) and Root Counter 1.
- STAR COAST (1024 cells) and draw distance: the GBA map streamer budget (reserve 0x0201b870..) disappears: cells live in RAM/CD (1024 cells x ~64 B headers + geometry streamed from CD in rings); draw distance is limited by GTE throughput (about 60-90k polys/s realistic, i.e. 2-4k polys/frame at 24 fps) and by OT depth; use fog and 2 LODs.
- Shared with the GBA build: all of stuntfox/src game logic (car, physics, campaign, mission glue, radio logic, ragdoll solver), content tools, music rendering; the PS1 build adds a `ps1/` directory (crt0, gpu, gte, cd, spu, pad, card, translator tool) selected by a build flag. Payback itself is shared as the same ROM input.

## 4. Stages (each ends in something to run)
Deliverable format: a `.cue` + `.bin` (MODE2/2352, CD-DA tracks as extra bin/wav entries) built on the user's machine from their ROM, plus a plain `.iso` first (DuckStation, PCSX-ReARMed and PCSXR load ISO). A bare PS-EXE is not an Android-friendly format. Needs: a BIOS for DuckStation (user's own), none for ReARMed's HLE (limited). The repo only holds the build tools.

Stages 4 and 5 can overlap two agents (sound/save vs ragdoll/big map).

## 5. Risks and numbers to watch
1. R1 CPU: translated Payback logic may exceed 50% of the R3000 (unmeasured). Mitigation: run Payback tick at 15 Hz, profile in stage 1, hand-port the top 10 hot functions to C (our engine already replaces the renderer).
2. R2 RAM: code 1.0-1.5 MiB translated; overlay arena 700 KiB; any pointer-compare code breaks model B. Mitigation: translator logs unsafe patterns; fall back to model A for flagged functions.
3. R3 2D layers: Payback's BG/OBJ/affine modes need an emulated PPU-lite; menus first.
4. R4 Accuracy: ARM semantic details (carry/overflow, unaligned loads, ldm/stm ordering, mul flags); the lockstep trace test covers it; Thumb coverage today is 99.5% (728 unsupported sites).
5. R5 Tools: no real PS1 BIOS or hardware here; PCSXR HLE is the only emulator; DuckStation compatibility is untested. Plan: first user build is a plain `.iso`, ask the user to try it in DuckStation with their BIOS and report.
6. R6 CD-DA/CD speed in emulators and ISO-only images (no audio tracks without a cue); the cue needs audio track BINs.
7. Legal: nothing from the ROM (code, assets, audio) is committed; build outputs stay on the user's machine.
